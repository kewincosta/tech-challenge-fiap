# Project state

## Decisions

| ID | Decision | Rationale | Status | Date |
| --- | --- | --- | --- | --- |
| AD-001 | Every table a route can address carries `id bigserial` for internal use and foreign keys, and `external_id uuid` for anything that leaves the process; join tables no route addresses keep a composite key of internal ids (ADR 0006) | One identifier rule across the schema: no enumerable key in a URL or payload, and compact indexes and foreign keys inside. Every write that references another table resolves an external id into an internal key at the repository boundary | active | 2026-08-30 |
| AD-002 | Money lives in the shared kernel, and the backend works in integer BRL cents everywhere; formatting and currency conversion belong to the client (ADR 0007) | Services, inventory and work orders need the same arithmetic, and their totals add up across modules. The columns are `bigint`, which TypeORM returns as strings, so every mapper converts | active | 2026-08-30 |
| AD-003 | Modules talk only through the `CommandBus` and the `QueryBus`, exchanging identifiers and DTOs (ADR 0008) | It was the pattern between `users` and `authorization`, and it kept the module boundary real | superseded by AD-012 | 2026-08-30 |
| AD-004 | A profile is a role on a user. Only `Customer` gets an aggregate of its own; Mechanic, Service advisor and Administrator do not (ADRs 0009 and 0010) | Customer carries workshop data with its own invariant, one identity per customer; the other profiles have no state or invariant beyond their access. A work order points at `customer_id` and at `assigned_mechanic_user_id` | active | 2026-08-30 |
| AD-005 | The group feature is removed from the authorization model: the four group tables, the Group aggregate and the `groups:read` and `groups:manage` permissions (ADR 0011) | Roles already bundle permissions for a set of users. Groups add a second level that only a second axis, such as a branch, a shift or a team, would need, and this workshop has none | active | 2026-08-30 |
| AD-006 | `SUPER_ADMIN` is created only by the seed or a direct insert, holds `roles:manage`, and is the only profile that can grant `ADMIN`. Role assignment refuses `SUPER_ADMIN`, and refuses `ADMIN` unless the actor holds `SUPER_ADMIN` (ADR 0012) | An operational administrator must not widen their own access, and the access model needs an owner below the API. The seed has to run before anybody can log in | active | 2026-08-30 |
| AD-007 | Audit records are append only and are written in the transaction of the aggregate whose facts they describe: `work_order_events` is written by `WorkOrderRepository.save`, never by an event subscriber (ADR 0021) | A subscriber runs after the commit, so a failure there loses an entry whose fact is already saved. Every domain event that feeds a trail carries its acting user | active | 2026-08-30 |
| AD-008 | A repository honours an ambient transaction: it takes its `EntityManager` from `currentEntityManager()`, and when there is none it opens its own through `runInNewTransaction`, which publishes that manager as the ambient one (ADRs 0023 and 0032) | A repository that always opened `dataSource.transaction` took a second connection and left two writes independent, which no test of the calling module could catch. Refined on 2026-10-29, so the key resolvers and owner reads a repository calls join its own transaction | active within one module; superseded by AD-017 for writes across modules | 2026-09-01 |
| AD-009 | An aggregate whose commands can run concurrently carries a `version` column. Its repository's `save` writes `WHERE id = :id AND version = :loadedVersion`, bumps the version, and throws `ConcurrentModificationError` (409) when no row matches; use cases carry no concurrency handling of their own (ADR 0024) | Two concurrent withdrawals on one work order both answered 200, and the second save overwrote the first. A guard in the repository covers every use case, the ones written later included. A concurrent write fails with 409, and nothing retries it | active | 2026-09-01 |
| AD-010 | A decision is recorded twice and cross-referenced: an `AD-NNN` row here and a numbered record in `docs/adr/`, each naming the other | The ADR carries the reasoning, and this log carries the summary a session reads first. A decision recorded in only one of them is a visible gap | active | 2026-09-02 |
| AD-011 | Use cases are plain classes with no framework import, decorator or injection token. Controllers call them directly, each module's composition root builds them with factory providers, repository contracts live in `application/ports`, and `@nestjs/cqrs` is gone (ADR 0026) | The dependency rule of the Clean Architecture study the project adopted on 2026-10-27: the core knows neither the framework nor the container. Every use case is wired by hand in its composition root | active | 2026-10-28 |
| AD-012 | A module reaches another only through a port it declares in `application/ports` and implements in its own infrastructure by calling the other module's public API, its `index.ts`. No `domain` or `application` file imports another module, and module dependencies have no cycle. Where the owner of some data already depends on the module that needs it, the consumer declares the interface, the owner implements it, and the root module binds the two (ADR 0027) | It avoids coupling between modules and dependency cycles, with every boundary explicit and checked by dependency-cruiser. Each need across modules costs a port, a gateway and a fake | active | 2026-10-28 |
| AD-013 | Each module queries only its own tables. Another module's internal key comes from the key resolver that module offers, and its data from its public API, in batch, composed in memory by the consumer. The shared schema and its foreign keys stay (ADR 0028) | It avoids coupling between modules and dependency cycles, and keeps each module responsible for its own data. A read across modules runs several batch queries and no longer comes from one snapshot | active | 2026-10-28 |
| AD-014 | `users`, `authentication` and `authorization` form one module, `identity`, each an area with its own layer folders (ADR 0029) | The three depend on one another in both directions, and the architecture documents already treat them as one bounded context | active | 2026-10-28 |
| AD-015 | Route-level permission checks stay in the HTTP guard, rules that depend on the data stay in the use cases, and each entry point authenticates and authorizes its own caller (ADR 0030) | A route permission depends on who calls and through which channel: a JWT, a trusted process, a webhook signature. The data rules are business rules every entry point shares | active | 2026-10-28 |
| AD-016 | Four patterns stay beyond the dependency rule: command and query use cases, one class per use case, Nest's dependency injection confined to the composition roots, and domain events published through a port to an in-process dispatcher that does not wait for its subscribers (ADR 0031) | The study treats them as choices that need their own justification, and ADR 0031 gives one per pattern | active | 2026-10-28 |
| AD-017 | No transaction writes the tables of two modules. Withdraw, return, deliver and cancel (`work-orders` and `inventory`) and customer registration (`customers` and `identity`) run as steps each module commits on its own. The orchestrating module keeps them in an outbox table, and a processor applies them, retries a failed one with a growing delay, and marks it failed at the attempt limit. The withdrawal and the registration compensate their first step; the other three retry their inventory step. Every receiving step is idempotent by operation id, the steps of a work order apply in the order they were recorded (an undo excepted), and a withdrawal's consumption counts for a restore, a settlement or a write-off only once its work order confirmed it (ADR 0033) | The user's decision of 2026-10-31. A shared transaction coupled two modules through the database connection, which caused the pool starvation fixed on 2026-10-29 (ADR 0032), and an outbox keeps the guarantee across a crash. A step that keeps failing needs an operator | active | 2026-10-31 |

## Follow-ups

Found during earlier features and left outside them, to plan when someone takes one:

- The Phase 2 API changes are the next feature, with their documentation and a Postman collection: opening a work order with services and parts, the status lookup, an endpoint for external budget approval notifications, the listing order and exclusion, and status updates by e-mail. Its open decisions are parts at reception (`PART_PLANNABLE_STATES` forbids them today), customer and vehicle data or ids at opening, where `CANCELED` goes in the listing, and how the external system authenticates on the approval route.
- Both step tables lack an index on `(status, due_at)`, `work_order_stock_steps` lacks one on `(work_order_id, id)`, and `DONE` steps have no retention rule.
- Two e2e cases fail now and then on random data: a CPF collision in `role-escalation` and a plate collision in `work-order-closing`.
- `docs/roteiro-video.md:95-100` and `:361` and `security/scripts/deliverable.ts:255` still name CQRS and the buses, and the video script counts nine migrations.
- `FindUserByDocumentUseCase` is unused, and some spec variables are still named `handler`.
- The inventory stock use cases publish their item events inside their transaction, before the commit. Nothing subscribes to them today.
